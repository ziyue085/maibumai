# 设计说明

写给两类读者：**未来的自己**（三个月后忘了为什么这么设计），以及**独立审核者**（要判断这套东西是否站得住）。

---

## 一、要解决的真实失败模式

先说清楚"什么叫做错了"，否则所有设计都无从评价。

用户问"这个值不值得买"，AI 的失败有五种：

| 失败 | 表现 | 后果 |
|---|---|---|
| **F1 逃避** | "要看你的需求""因人而异" | 用户白问一场 |
| **F2 说教** | "建议理性消费""非必需可以再想" | 用户被当成需要管束的人 |
| **F3 迎合** | "好评很多，性价比不错，可以入手" | 用户花错钱，AI 成了导购 |
| **F4 编造** | "这类一般 2000 左右""历史最低价" | 用户基于假信息决策 |
| **F5 自相矛盾** | 理由全指向暂缓，结论写"建议购买" | 输出不可信，也无法复盘 |

前三种是**立场问题**，后两种是**可靠性问题**。

v0.1 的设计目标是：**F4 和 F5 用代码结构性拦住；F1/F2/F3 用规则码体系约束。**

---

## 二、五个核心决策

### 决策 1：结论由规则码解析，不由模型宣布

**做法**：模型只能给理由码（22 个），结论由 `verdict.resolve()` 按固定优先级算出。

**为什么**：这是整个项目最重要的一条。

如果让模型直接输出结论，F5 就无法避免——模型会在理由和结论之间产生漂移，而且这种漂移**不可测试**。你无法为一个自然语言结论写断言。

改成"码 → 结论"之后：

- 结论变成纯函数，可以写夹具、可以跑变异测试。
- 模型即使想迎合，也过不了 `AUD_TIER_CONFLICT`。
- 复盘时能按码统计"我在哪类理由上判断失误"，而不是只知道"买错了"。

**代价**：模型必须先把判断翻译成码，多说一步。这一步会有摩擦，也可能翻译错（见「已知限制」第 1 条）。

### 决策 2：四类结论，而不是评分

**被否决的方案**：价值评分（0–100）、五档推荐度、加权总分。

**为什么否决**：

1. **虚假精度**。"这件东西 73 分"暗示了一个不存在的测量尺度。没人知道 73 分和 68 分的差别意味着什么。
2. **维度不可通约**。"健康收益 8 分 + 情绪价值 6 分 − 价格 4 分 = 10 分"这种加总没有意义——健康问题和娱乐消费本来就不该放进同一个天平。
3. **无法行动**。"73 分"不能告诉用户该干什么；"建议暂缓，双十一 ≤2500 就买"可以。

四类结论对应四种**不同的行动**，这是它能用的原因。

### 决策 3：证据独立成层，且能被阻断

**做法**：`evidence.check()` 独立校验来源等级、观测日期、价格冲突、日期越界。

**为什么**：

F4（编造）最典型的形态不是"凭空造一个数字"，而是：

- 拿两个月前的价格当现价（最常见）
- 拿一条评论当普遍口碑
- 用"这类产品一般……"代替查证
- 把用户口述价格当作市场价

这些都有**可判定的特征**——日期、来源类型、是否有链接。所以能写成代码。

关键的一条：**只有用户口述的价格，不能支撑"建议购买"**。因为"这个价合理"是一个关于市场的断言，而用户的口述不构成市场证据。这条规则由 `AUD_PRICE_UNVERIFIED` 执行。

### 决策 4：分三级，不是每笔都做研究

**做法**：≤100 元走 L1（三句话，不联网不留档）；超门槛或耐用品走 L3（全流程）。

**为什么**：为 29 元的手机壳做二十分钟研究，本身就是在浪费生命。**过度分析也是一种成本**，而且是最容易被"严谨"这个词掩盖的成本。

L1 的存在还有一个作用：它让 L3 的严谨变得可信。如果每笔都长篇大论，用户会学会跳过所有分析。

### 决策 5：零模型调用、零第三方依赖

**做法**：全部逻辑是标准库 Python，不调用任何 LLM API。

**为什么**：

- 需求 6 明确要求"避免不必要的模型调用"。最彻底的满足方式是**一次都不调**——判断所需的智能来自宿主模型，脚本只负责一致性。
- 引入 API 意味着 API Key 管理、费用、延迟、可用性风险，以及一个新的不可控输出源。
- 纯标准库意味着三年后拿出来还能跑，不会因为某个包改名而报废。

## 三、阈值：全是经验取值

必须说清楚：**下面的数字没有统计依据，是设计时的判断，可按个人情况改。**

| 参数 | 取值 | 依据 | 改法 |
|---|---|---|---|
| `small_amount_fastpath` | 100 元 | 低于这个数，研究的时间成本超过可能的损失 | `profile.behavior` |
| `single_purchase_threshold` | max(500, 月可支配 × 25%) | 低于 500 元，研究的时间成本超过可能的损失；超过月可支配四分之一，就会影响其它安排 | `calc.THRESHOLD_RATIO` |
| `BREACH_MULTIPLE` | 6 倍月可支配 | 相当于半年全部可支配收入，越过这条线通常意味着要借贷或挤压刚需 | `calc.py` 常量 |
| 价格保鲜期（快变品类） | 7 天 | 数码/服饰的促销周期通常以周计 | `evidence.STALE_DAYS` |
| 价格保鲜期（其他） | 14 天 | 家具家电价格变动慢，两周内通常稳定 | 同上 |
| 促销价保鲜期 | 3 天 | 活动随时结束，过夜就可能失效 | 同上 |
| 价格冲突阈值 | 15% | 低于 15% 的差异通常可由运费/券/会员价解释 | `evidence._PRICE_CONFLICT_RATIO` |
| `MIN_REASONS` | L1=1 / L2=2 / L3=3 | 少于这个数，结论无法复盘；再多会诱发凑数 | `verdict.MIN_REASONS` |
| 复盘周期 | 60 天 | 短于 30 天看不出真实使用率，长于 90 天用户已经忘了 | `profile.behavior.review_days` |

**一个自我提醒**：这些数字被写进代码，容易让人误以为它们有依据。它们没有。它们是**可调的默认值**，不是真理。

## 四、被否决的其他方案

| 方案 | 否决理由 |
|---|---|
| 评分卡 / 加权总分 | 虚假精度，维度不可通约，无法指导行动 |
| 直接让模型输出结论 | 不可测试、不可复现，F5 无法拦截 |
| 再调一次 LLM 做"二次判断" | 增加成本与延迟，且引入新的不可控源；一致性应该用代码保证，不是用另一个模型 |
| SQLite 存储 | 个人量级（每年几百条）用不上；JSONL 可读、可 diff、可手工修 |
| 与记账软件打通 | 超出范围；记账回答"钱花哪了"，本 Skill 回答"该不该花" |
| 爬虫自动比价 | 维护成本极高（反爬、页面改版），且容易违反平台条款；改为"模型联网查 + 人工复核" |
| 给用户打"消费人格"标签 | 贴标签会固化偏见，且无法证伪 |
| 强制每次都要填完整画像 | 首次使用门槛过高，用户会直接放弃；改为渐进式（用到才问） |

## 五、已知限制

按严重程度排序。**这些不是待办事项，是设计边界。**

### 1. 规则引擎保证一致性，不保证正确性（最根本）

`verdict.resolve()` 能保证"结论与理由不矛盾"，但保证不了"理由选对了"。

如果模型把"重复购买"错判成"替换需求"，得出的结论会**内部完全自洽，但实际是错的**。

这是本设计的根本边界：**它防的是自相矛盾和编造，不是判断力本身。** 判断力仍然取决于模型对场景的理解。

缓解手段：`examples/` 里的四个案例就是给模型看的判断锚点；`decision-rules.md` 里每个码都写了"常见误用"。

### 2. 规则码覆盖不全

22 个码覆盖了理性的消费维度，但漏掉了真实决策里的重要因素：

- **人情压力**（"同事都买了""不买不合群"）
- **面子与身份**（"这个场合得穿得体面"）
- **家庭关系**（"我妈想要"）
- **时间压力下的将就**（"现在就得用，来不及比价"）

这些不是"不理性"，是另一种理性。当前版本只能把它们塞进 `EMOTIONAL_VALUE_LEGIT` 或 `INFO_GAP`，语义不够精确。

### 3. 使用频率依赖用户自报

整套算术建立在"预计每周用几次"上，而这个数字是用户说的，天然乐观。

缓解：复盘会算出高估倍数并回灌。但这需要用户真的回来复盘——**不回报就没有校准**。

### 4. 无法验证用户的陈述

用户说"旧的那个坏了"，系统无从核实。`owned.json` 的 `condition` 字段完全靠自觉。

这是隐私设计的必然代价：不上传、不核验，就必然依赖诚实。

### 5. 取价能力受限于公开页面

需要登录、有反爬、或者只在 App 内显示的页面，取不到就是取不到。此时只能是"未核实"，用户可能觉得"你怎么连这个都查不到"。

### 6. 阈值是经验值

见第三节。可能对某些人不合适，尤其是收入波动大或家庭共同开支的情况。

### 7. 中文语境的句式检测是启发式的

`AUD_VAGUE_PHRASE` 靠词表匹配，"看你自己"能被抓到，但"这个还是要结合你的实际情况来看"抓不到。

词表可以扩充，但永远追不上语言的变体。它的作用是**提高敷衍的成本**，不是杜绝敷衍。

### 8. L1 不留档，小额高频消费看不见

≤100 元的判断不写账本——这是为了不打扰用户，代价是**最容易失控的那类消费反而没有记录**。

20 笔 80 元的东西，单笔都不值得研究，加起来 1600 元。这正是"拿铁因子"型问题的形态，而当前版本对它无感。

### 9. 复盘依赖用户主动

`due` 只能列出"已标记购买且超期"的记录。用户不执行 `outcome --bought yes`，就永远不会出现在待复盘里。

这是刻意的：不该在用户没确认购买时反复追问。但没有确认就没有校准，这套系统的长期价值一半建立在这上面。

### 10. 单一币种（v0.2 已缓解）

v0.1 的 `currency` 字段是摆设。v0.2 加了币种归一：外币必须有 `fx` 汇率证据，否则阻断。
但仍不支持多币种账户、也做不了实时汇率——汇率本身靠模型去查，过期只警告不阻断。

## 六、可维护性

- **加一条规则**：在 `verdict.RULE_TIER` 加码 → 在 `decision-rules.md` 写判据 → 在 `verdict_cases.json` 加正反两个夹具 → 跑变异测试确认。
- **改阈值**：改常量 → 跑回归 → 看哪些夹具受影响。夹具挂了说明改动的影响面比预想大。
- **加品类知识**：往 `archetypes.md` 加一节，不需要改代码。
- **迁移到别的宿主**：`scripts/` 是纯标准库 CLI，任何能执行命令的 Agent 都能用。SKILL.md 是 WorkBuddy 格式，换成别的格式只需重写这一个文件。

---

## 七、开发中修掉的缺陷

留档，说明这些设计不是一次想清楚的，也提醒后来者：**规则之间的耦合往往在真实场景里才暴露。**

| 缺陷 | 表现 | 修法 |
|---|---|---|
| 证据为空即阻断 | "我想买个 iPad"式的暂缓记录全被拒收 | `EV_NONE` 降为警告；真正阻断的是"要求价格却拿不出来" |
| 阻断不区分结论类型 | 因价格过期而暂缓的记录，反被过期价格阻断落账 | `ok` 按结论类型门控：只有要买/换方案才要求证据全绿 |
| 跨商品比价被判为冲突 | 品牌款 2680 vs 国产同类 1280，触发"价差 109%"警告 | 证据加 `subject: target/reference`，只在同一商品内部比价 |
| 体验型消费算单次成本 | 680 元演唱会 = "每次 680 元"，荒谬 | `experience` 类不算单次成本 |
| 订阅按次摊 | 月付 30 元 ÷ 30 次 = 0.08 元/次，错的框架 | 订阅改为年化成本 |
| L1 只对部分品类生效 | 29 元手机壳被判成 L2，要求两条理由 | 分级只看金额，只有订阅单列 |

最后一条尤其说明问题：分级逻辑最初写的是"低价 **且** 非耐用品"，结果手机壳（数码配件）永远进不了快速通道。**规则写得太"聪明"，反而会在边角失效。**

## 八、如果重来一次

三件事会做得不一样：

1. **规则码再少一半**。22 个里，`LOW_REGRET_RISK` 和 `SUBSTITUTE_INADEQUATE` 的使用频率会很低，实际起作用的是十来个。码越多，模型选错的概率越高。
2. **先做复盘，再做判断**。复盘数据（"你通常高估 3 倍"）的说服力远大于任何规则推理，但它需要先积累记录。冷启动阶段的说服力天然弱。
3. **L1 的边界再放宽**。100 元的线可能偏低，200 元以内其实都不值得研究。

## 九、v0.2 的返工：财务从"算给模型看"变成"引擎强制"

第一轮独立审核抓到十个问题，其中两个是同一个根因，也是这次返工的核心。

### 9.1 根因：算出来的结论没有人用

v0.1 的 `calc.budget_status()` 会算出 `breach`，然后把它放进 `numbers.budget` 里，**就此结束**。
是否把它转成 `BUDGET_BREACH` 理由码，全靠模型自觉。

结果是：18000 元的相机、月可支配 2000 元、自设上限 3000 元，只要模型不提预算，引擎就给出"建议购买"。
这不是模型不听话，是**架构把决定权放错了地方**。

### 9.2 改法：事实由引擎注入，判断才留给模型

| 谁 | 负责什么 |
|---|---|
| 模型 | 取证、追问、判断需求真假、选替代方案 |
| 引擎 | 从画像与价格**推导**预算、硬上限、约束，并把结论强制写进理由码 |

`BUDGET_BREACH`、`BUDGET_TIGHT`、`AFFORDABLE_WITHIN_BUDGET`、`CONSTRAINT_VIOLATION` 现在由引擎自动追加，
模型给不给都一样。审核时也把它们单列：**不计入"模型给了几条理由"，不算它的功课**。

这条改动的意义超出财务本身——它确立了一个分界：
**凡是能从数据推导出来的事实，都不该交给模型自由裁量。**

### 9.3 三道门：把"证据不可信"和"逻辑不自洽"分开

v0.1 只有一个 `ok`。于是"价格过期"这种**正常的暂缓理由**会把整条记录判为不合格，
而"理由与结论矛盾"这种**真正的错误**反而和它混在同一个列表里。

v0.2 拆成 `financial` / `integrity` / `coherence` 三道门，各自报告。典型效果：

- 因价格过期而暂缓 → `integrity` 不通过，`coherence` 通过，**记录可以落账**（P13）
- 暂缓却没写复查条件 → `integrity` 通过，`coherence` 不通过，**拒绝落账**（P14）

同一个 `ok` 表达不了这两件事。

### 9.4 等级：判据越少越难钻空子

v0.1 分级里有个"耐用品接近门槛即升级"的分支：
`kind == durable and price > threshold * 0.6`。

它让 29 元的手机壳进不了快车道（v0.1 已修一次），v0.2 又被审核指出**等级可以被标低绕过审核**。
两次都指向同一件事：**分级条件越多，可被解释的空间越大。**

现在等级只由两个量决定：金额，以及订阅的年化金额。没有品类分支，没有"接近"这种模糊词。

### 9.5 剩下的问题

这轮修的是"能不能被绕过"，不是"判断准不准"。

规则引擎仍然只能保证：结论和理由不矛盾、数字有出处、该拦的拦住。
**它保证不了理由选对了。** 三个真实会话跑下来，有两条我认为偏保守（见 `tests/natural-language-20261029.md`），
那是判断力问题，不是代码问题——只能靠复盘数据的累积慢慢校正。
