# 设计说明

写给两类读者：**未来的自己**（三个月后忘了为什么这么设计），以及**独立审核者**（要判断这套东西是否站得住）。

---

## 一、要解决的真实失败模式

先说清楚"什么叫做错了"，否则所有设计都无从评价。

用户问"这个值不值得买"，AI 的失败有五种：

| 失败 | 表现 | 后果 |
|---|---|---|
| **F1 逃避** | "要看你的需求""因人而异" | 用户白问一场 |
| **F2 说教** | "建议理性消费""非必需可以再想" | 用户被当成需要管束的人 |
| **F3 迎合** | "好评很多，性价比不错，可以入手" | 用户花错钱，AI 成了导购 |
| **F4 编造** | "这类一般 2000 左右""历史最低价" | 用户基于假信息决策 |
| **F5 自相矛盾** | 理由全指向暂缓，结论写"建议购买" | 输出不可信，也无法复盘 |

前三种是**立场问题**，后两种是**可靠性问题**。

v0.1 的设计目标是：**F4 和 F5 用代码结构性拦住；F1/F2/F3 用规则码体系约束。**

---

## 二、五个核心决策

### 决策 1：结论由规则码解析，不由模型宣布

**做法**：模型只能给理由码（22 个），结论由 `verdict.resolve()` 按固定优先级算出。

**为什么**：这是整个项目最重要的一条。

如果让模型直接输出结论，F5 就无法避免——模型会在理由和结论之间产生漂移，而且这种漂移**不可测试**。你无法为一个自然语言结论写断言。

改成"码 → 结论"之后：

- 结论变成纯函数，可以写夹具、可以跑变异测试。
- 模型即使想迎合，也过不了 `AUD_TIER_CONFLICT`。
- 复盘时能按码统计"我在哪类理由上判断失误"，而不是只知道"买错了"。

**代价**：模型必须先把判断翻译成码，多说一步。这一步会有摩擦，也可能翻译错（见「已知限制」第 1 条）。

### 决策 2：四类结论，而不是评分

**被否决的方案**：价值评分（0–100）、五档推荐度、加权总分。

**为什么否决**：

1. **虚假精度**。"这件东西 73 分"暗示了一个不存在的测量尺度。没人知道 73 分和 68 分的差别意味着什么。
2. **维度不可通约**。"健康收益 8 分 + 情绪价值 6 分 − 价格 4 分 = 10 分"这种加总没有意义——健康问题和娱乐消费本来就不该放进同一个天平。
3. **无法行动**。"73 分"不能告诉用户该干什么；"建议暂缓，双十一 ≤2500 就买"可以。

四类结论对应四种**不同的行动**，这是它能用的原因。

### 决策 3：证据独立成层，且能被阻断

**做法**：`evidence.check()` 独立校验来源等级、观测日期、价格冲突、日期越界。

**为什么**：

F4（编造）最典型的形态不是"凭空造一个数字"，而是：

- 拿两个月前的价格当现价（最常见）
- 拿一条评论当普遍口碑
- 用"这类产品一般……"代替查证
- 把用户口述价格当作市场价

这些都有**可判定的特征**——日期、来源类型、是否有链接。所以能写成代码。

关键的一条：**只有用户口述的价格，不能支撑"建议购买"**。因为"这个价合理"是一个关于市场的断言，而用户的口述不构成市场证据。这条规则由 `AUD_PRICE_UNVERIFIED` 执行。

### 决策 4：分三级，不是每笔都做研究

**做法**：≤100 元走 L1（三句话，不联网不留档）；超门槛或耐用品走 L3（全流程）。

**为什么**：为 29 元的手机壳做二十分钟研究，本身就是在浪费生命。**过度分析也是一种成本**，而且是最容易被"严谨"这个词掩盖的成本。

L1 的存在还有一个作用：它让 L3 的严谨变得可信。如果每笔都长篇大论，用户会学会跳过所有分析。

### 决策 5：零模型调用、零第三方依赖

**做法**：全部逻辑是标准库 Python，不调用任何 LLM API。

**为什么**：

- 需求 6 明确要求"避免不必要的模型调用"。最彻底的满足方式是**一次都不调**——判断所需的智能来自宿主模型，脚本只负责一致性。
- 引入 API 意味着 API Key 管理、费用、延迟、可用性风险，以及一个新的不可控输出源。
- 纯标准库意味着三年后拿出来还能跑，不会因为某个包改名而报废。

## 三、阈值：全是经验取值

必须说清楚：**下面的数字没有统计依据，是设计时的判断，可按个人情况改。**

| 参数 | 取值 | 依据 | 改法 |
|---|---|---|---|
| `small_amount_fastpath` | 100 元 | 低于这个数，研究的时间成本超过可能的损失 | `profile.behavior` |
| `single_purchase_threshold` | max(500, 月可支配 × 25%) | 低于 500 元，研究的时间成本超过可能的损失；超过月可支配四分之一，就会影响其它安排 | `calc.THRESHOLD_RATIO` |
| `BREACH_MULTIPLE` | 6 倍月可支配 | 相当于半年全部可支配收入，越过这条线通常意味着要借贷或挤压刚需 | `calc.py` 常量 |
| 价格保鲜期（快变品类） | 7 天 | 数码/服饰的促销周期通常以周计 | `evidence.STALE_DAYS` |
| 价格保鲜期（其他） | 14 天 | 家具家电价格变动慢，两周内通常稳定 | 同上 |
| 促销价保鲜期 | 3 天 | 活动随时结束，过夜就可能失效 | 同上 |
| 价格冲突阈值 | 15% | 低于 15% 的差异通常可由运费/券/会员价解释 | `evidence._PRICE_CONFLICT_RATIO` |
| `MIN_REASONS` | L1=1 / L2=2 / L3=3 | 少于这个数，结论无法复盘；再多会诱发凑数 | `verdict.MIN_REASONS` |
| 复盘周期 | 60 天 | 短于 30 天看不出真实使用率，长于 90 天用户已经忘了 | `profile.behavior.review_days` |

**一个自我提醒**：这些数字被写进代码，容易让人误以为它们有依据。它们没有。它们是**可调的默认值**，不是真理。

## 四、被否决的其他方案

| 方案 | 否决理由 |
|---|---|
| 评分卡 / 加权总分 | 虚假精度，维度不可通约，无法指导行动 |
| 直接让模型输出结论 | 不可测试、不可复现，F5 无法拦截 |
| 再调一次 LLM 做"二次判断" | 增加成本与延迟，且引入新的不可控源；一致性应该用代码保证，不是用另一个模型 |
| SQLite 存储 | 个人量级（每年几百条）用不上；JSONL 可读、可 diff、可手工修 |
| 与记账软件打通 | 超出范围；记账回答"钱花哪了"，本 Skill 回答"该不该花" |
| 爬虫自动比价 | 维护成本极高（反爬、页面改版），且容易违反平台条款；改为"模型联网查 + 人工复核" |
| 给用户打"消费人格"标签 | 贴标签会固化偏见，且无法证伪 |
| 强制每次都要填完整画像 | 首次使用门槛过高，用户会直接放弃；改为渐进式（用到才问） |

## 五、已知限制

按严重程度排序。**这些不是待办事项，是设计边界。**

### 1. 规则引擎保证一致性，不保证正确性（最根本）

`verdict.resolve()` 能保证"结论与理由不矛盾"，但保证不了"理由选对了"。

如果模型把"重复购买"错判成"替换需求"，得出的结论会**内部完全自洽，但实际是错的**。

这是本设计的根本边界：**它防的是自相矛盾和编造，不是判断力本身。** 判断力仍然取决于模型对场景的理解。

缓解手段：`examples/` 里的四个案例就是给模型看的判断锚点；`decision-rules.md` 里每个码都写了"常见误用"。

### 2. 规则码覆盖不全

22 个码覆盖了理性的消费维度，但漏掉了真实决策里的重要因素：

- **人情压力**（"同事都买了""不买不合群"）
- **面子与身份**（"这个场合得穿得体面"）
- **家庭关系**（"我妈想要"）
- **时间压力下的将就**（"现在就得用，来不及比价"）

这些不是"不理性"，是另一种理性。当前版本只能把它们塞进 `EMOTIONAL_VALUE_LEGIT` 或 `INFO_GAP`，语义不够精确。

### 3. 使用频率依赖用户自报

整套算术建立在"预计每周用几次"上，而这个数字是用户说的，天然乐观。

缓解：复盘会算出高估倍数并回灌。但这需要用户真的回来复盘——**不回报就没有校准**。

### 4. 无法验证用户的陈述

用户说"旧的那个坏了"，系统无从核实。`owned.json` 的 `condition` 字段完全靠自觉。

这是隐私设计的必然代价：不上传、不核验，就必然依赖诚实。

### 5. 取价能力受限于公开页面

需要登录、有反爬、或者只在 App 内显示的页面，取不到就是取不到。此时只能是"未核实"，用户可能觉得"你怎么连这个都查不到"。

### 6. 阈值是经验值

见第三节。可能对某些人不合适，尤其是收入波动大或家庭共同开支的情况。

### 7. 中文语境的句式检测是启发式的

`AUD_VAGUE_PHRASE` 靠词表匹配，"看你自己"能被抓到，但"这个还是要结合你的实际情况来看"抓不到。

词表可以扩充，但永远追不上语言的变体。它的作用是**提高敷衍的成本**，不是杜绝敷衍。

### 8. L1 不留档，小额高频消费看不见

≤100 元的判断不写账本——这是为了不打扰用户，代价是**最容易失控的那类消费反而没有记录**。

20 笔 80 元的东西，单笔都不值得研究，加起来 1600 元。这正是"拿铁因子"型问题的形态，而当前版本对它无感。

### 9. 复盘依赖用户主动

`due` 只能列出"已标记购买且超期"的记录。用户不执行 `outcome --bought yes`，就永远不会出现在待复盘里。

这是刻意的：不该在用户没确认购买时反复追问。但没有确认就没有校准，这套系统的长期价值一半建立在这上面。

### 10. 单一币种（v0.2 已缓解）

v0.1 的 `currency` 字段是摆设。v0.2 加了币种归一：外币必须有 `fx` 汇率证据，否则阻断。
但仍不支持多币种账户、也做不了实时汇率——汇率本身靠模型去查，过期只警告不阻断。

## 六、可维护性

- **加一条规则**：在 `verdict.RULE_TIER` 加码 → 在 `decision-rules.md` 写判据 → 在 `verdict_cases.json` 加正反两个夹具 → 跑变异测试确认。
- **改阈值**：改常量 → 跑回归 → 看哪些夹具受影响。夹具挂了说明改动的影响面比预想大。
- **加品类知识**：往 `archetypes.md` 加一节，不需要改代码。
- **迁移到别的宿主**：`scripts/` 是纯标准库 CLI，任何能执行命令的 Agent 都能用。SKILL.md 是 WorkBuddy 格式，换成别的格式只需重写这一个文件。

---

## 七、开发中修掉的缺陷

留档，说明这些设计不是一次想清楚的，也提醒后来者：**规则之间的耦合往往在真实场景里才暴露。**

| 缺陷 | 表现 | 修法 |
|---|---|---|
| 证据为空即阻断 | "我想买个 iPad"式的暂缓记录全被拒收 | `EV_NONE` 降为警告；真正阻断的是"要求价格却拿不出来" |
| 阻断不区分结论类型 | 因价格过期而暂缓的记录，反被过期价格阻断落账 | `ok` 按结论类型门控：只有要买/换方案才要求证据全绿 |
| 跨商品比价被判为冲突 | 品牌款 2680 vs 国产同类 1280，触发"价差 109%"警告 | 证据加 `subject: target/reference`，只在同一商品内部比价 |
| 体验型消费算单次成本 | 680 元演唱会 = "每次 680 元"，荒谬 | `experience` 类不算单次成本 |
| 订阅按次摊 | 月付 30 元 ÷ 30 次 = 0.08 元/次，错的框架 | 订阅改为年化成本 |
| L1 只对部分品类生效 | 29 元手机壳被判成 L2，要求两条理由 | 分级只看金额，只有订阅单列 |

最后一条尤其说明问题：分级逻辑最初写的是"低价 **且** 非耐用品"，结果手机壳（数码配件）永远进不了快速通道。**规则写得太"聪明"，反而会在边角失效。**

## 八、如果重来一次

三件事会做得不一样：

1. **规则码再少一半**。22 个里，`LOW_REGRET_RISK` 和 `SUBSTITUTE_INADEQUATE` 的使用频率会很低，实际起作用的是十来个。码越多，模型选错的概率越高。
2. **先做复盘，再做判断**。复盘数据（"你通常高估 3 倍"）的说服力远大于任何规则推理，但它需要先积累记录。冷启动阶段的说服力天然弱。
3. **L1 的边界再放宽**。100 元的线可能偏低，200 元以内其实都不值得研究。

## 九、v0.2 的返工：财务从"算给模型看"变成"引擎强制"

第一轮独立审核抓到十个问题，其中两个是同一个根因，也是这次返工的核心。

### 9.1 根因：算出来的结论没有人用

v0.1 的 `calc.budget_status()` 会算出 `breach`，然后把它放进 `numbers.budget` 里，**就此结束**。
是否把它转成 `BUDGET_BREACH` 理由码，全靠模型自觉。

结果是：18000 元的相机、月可支配 2000 元、自设上限 3000 元，只要模型不提预算，引擎就给出"建议购买"。
这不是模型不听话，是**架构把决定权放错了地方**。

### 9.2 改法：事实由引擎注入，判断才留给模型

| 谁 | 负责什么 |
|---|---|
| 模型 | 取证、追问、判断需求真假、选替代方案 |
| 引擎 | 从画像与价格**推导**预算、硬上限、约束，并把结论强制写进理由码 |

`BUDGET_BREACH`、`BUDGET_TIGHT`、`AFFORDABLE_WITHIN_BUDGET`、`CONSTRAINT_VIOLATION` 现在由引擎自动追加，
模型给不给都一样。审核时也把它们单列：**不计入"模型给了几条理由"，不算它的功课**。

这条改动的意义超出财务本身——它确立了一个分界：
**凡是能从数据推导出来的事实，都不该交给模型自由裁量。**

### 9.3 三道门：把"证据不可信"和"逻辑不自洽"分开

v0.1 只有一个 `ok`。于是"价格过期"这种**正常的暂缓理由**会把整条记录判为不合格，
而"理由与结论矛盾"这种**真正的错误**反而和它混在同一个列表里。

v0.2 拆成 `financial` / `integrity` / `coherence` 三道门，各自报告。典型效果：

- 因价格过期而暂缓 → `integrity` 不通过，`coherence` 通过，**记录可以落账**（P13）
- 暂缓却没写复查条件 → `integrity` 通过，`coherence` 不通过，**拒绝落账**（P14）

同一个 `ok` 表达不了这两件事。

### 9.4 等级：判据越少越难钻空子

v0.1 分级里有个"耐用品接近门槛即升级"的分支：
`kind == durable and price > threshold * 0.6`。

它让 29 元的手机壳进不了快车道（v0.1 已修一次），v0.2 又被审核指出**等级可以被标低绕过审核**。
两次都指向同一件事：**分级条件越多，可被解释的空间越大。**

现在等级只由两个量决定：金额，以及订阅的年化金额。没有品类分支，没有"接近"这种模糊词。

### 9.5 剩下的问题

这轮修的是"能不能被绕过"，不是"判断准不准"。

规则引擎仍然只能保证：结论和理由不矛盾、数字有出处、该拦的拦住。
**它保证不了理由选对了。** 三个真实会话跑下来，有两条我认为偏保守（见 `tests/natural-language-20261029.md`），
那是判断力问题，不是代码问题——只能靠复盘数据的累积慢慢校正。

## 十、v0.3：把"一个人"装进模型，而不是把规则写死

第三轮审核八项，加上"私人画像要真的像我"这个要求。有两件事值得单独说。

### 10.1 6 倍月收入是个错误的红线

v0.2 用"价格 > 月可支配 × 6 → 不建议购买"当硬拦截。对一个工资稳定、没有存量的人，这个数还算合理；
对一个**有储蓄、收入不稳定**的人（学生、自由职业、间歇接活），它问的是错的问题。

他们真正的问题不是"月收入撑不住"，而是"这笔钱该不该从存量里出"。
拿月收入当分母，等于假装那笔储蓄不存在——而这笔储蓄恰恰是他敢做长期决定的底气。

v0.3 改成四步：**月结余 → 可自由消费资金 → 存量 + 一年结余 → 都不够才算买不起**。
6 倍降级为"提示"，一年结余 + 存量才是"安全底线"。

配套的一条：**"暂缓"和"否决"必须分开**。要攒几个月、要从存量里出，都是时间问题，不是能力问题。
把它们都判成"不建议购买"，系统就变成了一个只会说不行的人。

### 10.2 历史数字不是现值

用户给了一份带日期的资产快照。最省事的做法是直接填进画像——然后所有判断都建立在一个可能已经过期的数字上。

v0.3 加了 `confirmed` 字段：`seed` 写入的历史值默认未确认，**不参与计算**，`brief` 里显示"（某日记录，待确认）"。
用户说一句"还是这样"，才算数。

这条和"过期即未知"是同一个原则的两个面：**不确定的数据，宁可当作没有，也不要当作有。**

### 10.3 已有资源是判断的一部分，但不是否决理由

"我已经有三台服务器了"不等于"不能再买第四台"——可能新项目确实要 8G 内存。
但"完全不提我已经有三台"是失职。

所以引擎只做两件事：列出子品类相同的在用资源、算出在用订阅的月费合计；
如果结论是"建议购买"却完全没提，给一条警告。

匹配只看**子品类**。用顶层品类会把"买平板"和"已有手机、笔记本"判成重复——
这种误报一旦出现，用户就会学会忽略所有提示，比不提示更糟。

### 10.4 复利不是论据

把"这 3000 块十年后是 6477"当成反对购买的理由，是这套系统最容易变得讨厌的地方。

收益率是用户自己设的**假设**，不是他能拿到的收益。所以：没设就不算；设了必须写"假设，可能亏损"；
并且不能反复强调——说一次是信息，说三次是恐吓。

消费的收益是真实的：情绪价值、便利、效率、少受的罪。它们要进决策，不能被折现成一个吓人的数字抹掉。

## 十一、v0.4：结论与事实必须一致

第四轮审核的七条里，有六条是同一个病的不同症状：**系统知道某件事不成立，但仍然给出了结论。**

- 知道结余是估的，还是说"在预算内"；
- 知道替代品没价格，还是说"换成它"；
- 知道门槛没确认，还是按它分级；
- 知道账本要写归一后的理由，写的时候还是抄了原始输入。

共同点：检查做了，**检查结果没有权力**。这一轮改的就是把检查结果变成结论的输入。

### 11.1 三道闸门统一成一句话

以前分三处：`financial` 门给 BLOCK、`coherence` 门给 BLOCK、`integrity` 门给 BLOCK。
但"结论该不该降级"散在各处判断，很容易漏。

现在的规则只有一句：**没确认的承受力，不能支撑"买得起"。**

于是：

| 情况 | 旧行为 | 新行为 |
|---|---|---|
| 主结构（收入/支出）都缺 | BUY + 拦住记账 | **暂缓**，说明缺什么 |
| 结余是上界，且吃掉一半以上 | BUY + 拦住记账 | **暂缓** |
| 结余是上界，但只吃掉 40% | BUY + 拦住记账 | **购买**（够用就别折腾） |
| 存量覆盖、结余是估的 | BUY + 拦住记账 | **购买**（结余不是决定因素） |
| 金额还没定下来 | BUY + 拦住记账 | **暂缓** |

第二行和第三行之间的区别是这次唯一新增的判断：**50% 容忍度**。
缺的储蓄与投资额要吃掉一半以上结余才会翻转结论，剩下靠判断；这是经验值，写在 README 的已知限制里。

### 11.2 "不合格的替代方案"必须降级，不是加警告

旧版对替代品缺价格、缺周期、预算紧都只给 WARN。结果是：结论照样是「建议替换方案」，
用户看到的是一个**没有价格的推荐**。

现在替代品过六关（名称/价格/来源/周期/预算/报价出处），缺一关直接降为暂缓，
并把"差哪一项"写进 `problems`。**这不是变严格，是把"推荐"这个词的责任补上。**

副作用是 SWITCH 变难了。所以必须有一条反向用例守着（A2、A21）：合格的替代品必须能给出 SWITCH，
否则这套规则会退化成"一律暂缓"——那是另一种失败。

### 11.3 账本不是日志，是证据

`judge` 原来写 `draft["reasons"]`。这意味着判定阶段辛苦清掉的 `enforced` 伪造标记、
换算过的外币金额，到了账本里全部还原成原始输入。

一个月后回看这条记录，你会看到"NEED_REAL 是引擎强制判定的"这种荒唐事实。

现在账本只写 `result["reasons"] / result["evidence"] / result["alternative"]`，
并且新增 `ledger` 测试套件：它跑完整判定，再断言落盘内容，而不是断言函数返回值。

### 11.4 Windows 不是"顺便支持"

实际使用环境是 Windows。三个坑只有真跑才会遇到：

1. 控制台默认 GBK / cp1252，`print` 中文直接抛 `UnicodeEncodeError`；
2. 用户名是中文时，数据目录路径带非 ASCII；
3. 输出重定向到文件时，编码跟着系统代码页走，读回来是乱码。

修法是启动时把 stdout/stderr 重设成 UTF-8（失败就退回默认，不能因为改编码反而起不来）。
CI 加了 Windows job，覆盖 `chcp 65001` 与 `chcp 936` 两种代码页，以及中文目录名。

### 11.5 一个自己撞出来的矛盾：钱不够，但有更便宜的

跑替换方案那个例子时发现：2680 的椅子、月结余 1000，替代品 180 元。
结论是「建议替换方案」，而财务提示写着「结论已被强制为暂缓」。

两边都"对"：椅子确实要跨月；换成 180 的确实不用。错的是它们同时在说话。

根因是优先级表把「硬拦截」当成一整块。但 `BUDGET_BREACH` 和 `DUP_OWNED` 不是一回事：

- `DUP_OWNED` 否定的是**这件事**（你已经有了）；
- `BUDGET_BREACH` 否定的是**这个价格**（这个买法）。

所以规则补了一条例外：只被钱挡住时，一个合格且买得起的替代方案可以让位到「建议替换方案」。
`DUP_OWNED`、`SCAM_SIGNAL`、`CONSTRAINT_VIOLATION` 不让位。

这也是这套系统该有的立场——**说"不行"很容易，说"那怎么办"才有用。**

### 11.6 还没解决的

- 50% 容忍度和 12 倍安全底线仍是经验值，没有数据支撑。
- 替代品的报价证据靠模型自觉补；不补就退化成暂缓，用户可能觉得"你怎么老让我等"。
- 规则码依然不覆盖人情压力、面子、家庭共同决策。
- 判断力本身没变好——这一轮提高的是"不撒谎"的下限，不是"看得准"的上限。

## 十二、v0.5：边界不是边角料

这一轮五个问题，四个都发生在「边界」上——不是主流程错了，是**主流程之外的那一格**没定义清楚。
而用户踩到的，往往就是那一格。

### 12.1 "不知道"和"没有"是两件事

`budget_status()` 里有一行 `(spend or 0)`。它把「可动用存量未知」当成了「存量为零」。
后果不是保守，而是**凭空判人买不起**：月结余为负、现金没填，399 元也会被判 BUDGET_BREACH。

这类错误比"漏判"更伤：用户看到"你买不起"，而系统其实只是"不知道"。
一旦这种话出现第二次，整个工具的判断就不再被当真。

修法是把 `None` 一路传下去：存量未知就返回 `unknown`，只有**确认的零**才走安全底线。
代价是"未知"变多了，但"未知"至少不撒谎。

### 12.2 L2 也要知道钱从哪来

原本只有 L3 会因为"财务未知"降级，L2 直接放行。理由是"小额不值得问"。
但 300 元的判断同样要知道这笔钱会不会挤掉别的——它只是不需要查三个平台的价格，
不是不需要知道有没有钱。

现在只有 L1（百元以下快判）豁免。这条会让空画像用户的 L2 全部变成「暂缓」，
是有意的摩擦：**先告诉我三个数，再谈买不买。**

### 12.3 替代品的报价，只对得上数字不算数

旧逻辑是：有一条 `subject=alternative` 的证据、金额对得上 5%，就算有据。
于是「朋友说 600」和一条 40 天前的社区报价都能通过，甚至直接给出 SWITCH + ok=True。

现在要同时满足四件事：来源等级 ≤ 3、有可点开的链接、日期在保鲜期内、换算后金额一致。
缺哪一项就把哪一项写进 `problems`，结论降为暂缓。

同一个逻辑也补到了目标商品一侧：价格过期、无日期、未来日期、只有口述时，
引擎自动注入 `PRICE_STALE` / `PRICE_UNVERIFIED`。**不再有「输出购买 + 拦住落账」。**

### 12.4 时间边界：未来日期是最容易漏的一种

`fact_stale()` 用 `age > ttl` 判断过期。日期在未来时 `age` 是负数，永远不大于 ttl——
一条 2027 年的记录会被当成"最新鲜的数据"。

三处一起改：未来日期不可信；缺日期不可信（不是"默认今天"）；
`seed` 与 v1 迁移都不再拿今天顶替缺失的时间戳。迁移尤其重要——
把一个 2025 年的预算数字标成"今天确认"，等于伪造了一次用户确认。

### 12.5 测试也会撒谎

`_m26` 的 lambda 只有三个参数，而被测函数有五个。它"被捕获"了，因为一调用就 `TypeError`，
所有用例都失败。**变异测试报 33/33，其中一个是假的。**

修法不是改个 lambda 就完事，而是让运行器区分「断言失败」和「崩溃」：
每条结果带 `error` 标记，只有语义失败才算命中，只靠崩溃暴露的单独列为 `SURVIVED·崩溃`。

这条比前面四条都重要：**如果测试工具本身会骗人，前面四条修没修好你都不知道。**

### 12.6 还没解决的

- 「财务未知 → 暂缓」会让新用户的第一笔判断几乎全是暂缓。体验上有代价，需要好的追问话术。
- 替代品四关要求模型真的去查一条带链接的报价，查不到就只能给暂缓——可能显得"不肯下结论"。
- 未来日期的判定基于本机日期，跨时区/跨设备仍可能误判。
- 12 倍结余、50% 容忍度、7/14 天保鲜期仍是经验值。

## 十三、v0.6：没有证据，就没有结论

第五轮解决了"边界没定义"，第六轮解决的是更靠前的一格：
**证据本身有没有被真正检查过**。六个问题里，有四个的共同形态是——
系统确实"看到了"证据，但它看的那一眼是假的。

### 13.1 空集不等于没问题

`_target_price_defect()` 在"已索引的缺陷"里找价格问题。
一条报价证据都没有时，索引是空的，循环一次都不执行，返回"无缺陷"。
于是 900 元、财务齐全、买入理由完整的输入，可以直接得出 BUY。

这是典型的**把"没找到问题"当成"没有问题"**。
`EV_MISSING_KIND` 根本不进索引，所以靠索引永远发现不了。
修法是显式分两支：有证据但不可信 → 注入对应码；**完全没有证据 → 注入 `PRICE_UNVERIFIED`**。

教训很通用：**任何"扫描问题列表"的逻辑，都要先回答"列表为空意味着什么"。**

### 13.2 缺陷不能靠换个方案绕过

`resolve()` 原来 SWITCH 分支在前：目标价过期 + 替代品合格 → 输出「换方案」。
但目标价过期意味着**连"这个东西值不值得买"都还没定**，替代品再便宜也没有参照。

现在判定优先级变成六层：

```
hard_block（非金钱类 DONT_BUY）
  > price_veto（目标价不可信 → 暂缓）
  > money_only_block（买不起：有合格替代 → SWITCH，否则 DONT_BUY）
  > SWITCH（有问题则降为暂缓）
  > DEFER
  > BUY（必须有锚点）
  > DEFER
```

关键是 `price_veto` 只对**目标侧**生效：如果替代品自己带一条独立的合格报价，
价格参照就存在了，这时 SWITCH 仍然成立。区别「不可信的目标价」与
「替代品的独立合格报价」，是这一轮最容易做错的地方——
如果把两者混为一谈，规则就退化成"价格一有问题就一律暂缓"。

### 13.3 汇率是换算的唯一入口，也必须是唯一闸门

用户口述的汇率只要数值合理就被采纳，然后同时污染三处：价格归一化、预算、
替代品比较。现在汇率单独过五道关（来源等级、链接、日期、币种对、数值），
驳回后 `fx_rates()` 直接不返回它——**不是"提示一下继续用"，而是不参与任何计算**。

八个驳回码（`FX_NO_PAIR` / `SAME_PAIR` / `BAD_VALUE` / `WEAK_SOURCE` /
`NO_LINK` / `NO_DATE` / `FUTURE_DATE` / `STALE`）都带中文解释，
提示用户"为什么这条汇率不算数"，而不是笼统地说"信息不足"。

### 13.4 输入价与证据价冲突：别只拦落账

输入 900 元、可信报价 600 元，偏差 > 5%。原因可能是用户看错了、
也可能是报价是二手价。**原因未知 → 暂缓**，不是"按其中一个算下去"。

上一轮已经消灭了「输出 BUY + 拦住落账」，这一轮接着消灭
「按可疑价格算完了 + 拦住落账」。审计码 `AUD_PRICE_MISMATCH`
从落账阶段提到判定阶段生效。

**还没做**：如果决定采用证据价，应该重算等级、预算、结论与全部数字，
而不是把价格字段替换掉。目前只注入缺陷码，数字仍是输入值——
这是保守方向（不替用户改数），但确实留下了"数字和证据不一致"的中间态。

### 13.5 迁移不得替用户确认

v1 迁移原本沿用文件 `updated_at`，等于把一个旧数字标成"今天确认过的"。
现在迁移一律写 `confirmed=False`、`source="v1 画像迁移"`、沿用旧时间戳。
T10 专门守这条：即使文件时间恰好是今天，`confirmed` 也必须是 `False`。

原则是**：确认只能来自用户，不能来自文件的时间戳。**

### 13.6 链接长得像网址 ≠ 已核实

`valid_url()` 原来只检查结构，却被当成"报价已核实"在用。现在拆三层：

1. `url_syntax_ok()` —— 只是格式。对外不再宣称"已核实"。
2. 来源等级 + 有没有可点开的链接 + 日期是否在保鲜期。
3. `quote_content_problem()` —— 页面上的价，是不是你引用的那个价（> 2% 判不一致）。

配套的 `tests/real_quote_probe.py` 会联网抓一次真实报价页，
把状态码、页面价、内容 sha256 落进 `tests/fixtures/real-quote-record.json`，
之后测试用这条记录**离线回放**（Q0–Q3）。这样 CI 不需要联网，
也不会因为目标网站改版而随机变红。

### 13.7 这一轮的测试纪律

新增 7 条 pipeline 用例（N1–N7）+ 5 条 realquote 用例，全部暂缓类。
**暂缓类用例最容易"刷绿"**——一个永远输出暂缓的系统能过一半。
所以正向对照必须同步保留：N5（BUY）、Q1/Q3（SWITCH）、P34（L2 可买）。
变异测试 47 个，新增 8 个专门针对本轮修复，全部要求**语义断言**捕获，崩溃不算。

### 13.8 还没解决的

- 采用证据价后重算整条链路（13.4）未实现。
- 真实网页探测是**一次性抓取 + 离线回放**：它能证明"页面价与引用价比对"的逻辑可用，
  不能证明目标站点长期可访问或域名仍有效。
## 十四、v0.7：脏数据在进算式之前就该被拦住

第六轮解决的是"没有证据就没有结论"，第七轮遇到的是它的下一格：
**证据有了，但那是一份脏证据，而且它走完了整条链路。**
三个漏洞的形态完全一致——校验存在，但校验发生在**错误的位置**。

### 14.1 "先算出来再拦下来"是自欺欺人

`fx_rejection()` 只检查"是不是正数"。问题在于 `float('inf') > 0` 是真的，
`1e9 > 0` 也是真的，而 `"BTC"` 这种币种根本没人看。
于是 100 美元配上 USD/CNY=100000 会变成**一千万元**，
价格、等级、预算、结论全部基于这个数算完，最后才由预算门"碰巧"拦住——
而它之所以被拦住，只是因为这份画像恰好没填可动用现金。换个画像就是「不建议购买」。

汇率是这套系统里**唯一直接乘进价格**的数字。它的错误不是"多报了一点"，
而是"整个数量级错了"。所以必须在 `fx_rates()` 里就挡掉，
不能在下游设卡——下游任何一道门都只是在赌这个错会碰巧暴露。

三道新关：币种在可换算列表内、数值是**正的有限数**、数量级在 1e-4 ~ 1e4。
顺手把 `_positive_number()` 也改成要求有限——`inf` 的商品价同样不该进算式。

### 14.2 "有任意一条对得上"是最容易写错的一行

`_target_price_defect()` 原来是 `if not any(abs(v - price)/price <= 0.05 for v in values)`。
`any` 是这里最危险的词：官方 1200、社区 899、用户说 900，
它会拿 899 去凑——**低可信报价把官方价的冲突盖住了**。
它的语义问题不是"太宽松"，而是"用不可信的证据去证明可信的证据错了"。

改成只认最可信那一档（`credible_price_values()`）。
这个改动还顺带回答了一个以前没定义的问题：**同一等级来源互相打架怎么办**。
跨等级差异是常态（官方 1299 vs 第三方 999，报 WARN 说明差异即可）；
同等级差异是事故——两个官方来源报出不同的价，取平均、取最新、取便宜的都是在替用户挑。
新码 `EV_PRICE_CONFLICT`，结论降为暂缓。

`audit()` 里的 `AUD_PRICE_MISMATCH` 原来是同一个 `any`，
同步换成同一把尺——**两处口径不一致，比没有校验更危险**。

### 14.3 填假数据不能比老实留空更占便宜

`page_price` 这一格，旧逻辑只对"正数且不一致"报错，非正数一律当作"没填"。
于是 `page_price=0`、`page_price=-100`、`page_price=True`（布尔是 int 的子类）
都能让替代品拿到"页面核对过"的标记——
**填一个假页面价比老实留空还多拿一个等级。** 规则把人往错误的方向推。

`quote_content_problem()` 现在分两类：`PAGE_PRICE_INVALID`（不成立）
与 `QUOTE_CONTENT_MISMATCH`（自相矛盾），两类都拿不到 `page` 级。

这一类 bug 有个共同特征：**"缺失"和"无效"被合并处理了。**
`None`、0、False、NaN 在 Python 里都能被 `if not` 吞掉，但它们的语义完全不同：
`None` 是"我不知道"，0 是"我说是零"。合并处理等于奖励编数据。

### 14.4 测试怎么覆盖"JSON 写不出来的值"

`nan` / `inf` / `10**400` 不是合法的 JSON 数字。硬写进夹具，
得到的只是一个 `json.loads` 能读、别的工具读不了的文件。
所以新增 `fxguard` / `pageguard` 两个套件，用 Python 直接构造——
顺带也覆盖了"调用方传进来一个脏 dict"这条真实路径：
模型从网页里解析出 `Infinity` 是完全可能发生的。

### 14.5 别把"抓过一次页面"说成"内容已核实"

这一轮把真实网页探测的证明边界显式写进测试（Q4/Q5）：

- **能证明**：该 URL 在 `fetched_at` 那一刻返回的正文里出现过这个数字（含 sha256）。
- **不能证明**：域名是否官方、现在还是不是这个价、取证方是不是真读过页面。
- Q4 把最后一条固化成断言：填一个页面上根本没有的数字，系统照样判"页面核对过"。
  **这是已知限制，不是已修好的功能。** 测试把它钉住，是为了防止哪天有人宣称已解决。

sha256 只在生成那一刻有效；重放时不重新抓取，也验证不了线上内容有没有变。

### 14.6 还没解决的

- 采用证据价后重算整条链路（等级、预算、结论与全部数字）仍未实现：
  现在只注入缺陷码，数字仍是输入值。
- 汇率数量级边界（1e-4 ~ 1e4）仍是经验值，且只针对**当前支持的 9 个币种**校准过。
  新增小币种（如 VND、IDR）时必须重新校准，否则会被误杀。
- 同等级冲突的 5% 阈值与输入价口径的 5% 阈值共用一个数，
  不同品类（房价 vs 数据线）合理的容差并不相同。
- 真实网页探测是一次性抓取 + 离线回放，不能证明站点长期可访问。
- 自然语言链路（真实会话调用）本轮仍未重跑。
- `page_price` 无法自证来源（14.5）：要真正解决需要取证方把"页面片段"也带回来，
  而不是只带一个数。

## 十五、v0.8：过了闸门 ≠ 可信

第七轮修完"脏数据进链路"之后，复审又指出三处**合法但不可信**的数据被当成可信。
这三处的共性是：上一轮加的检查全部通过，但通过的原因是"没触发任何一条规则"，
而不是"有证据表明它可信"。

### 15.1 数值区间合法 ≠ 数值合理

`FX_MIN_RATE=1e-4` / `FX_MAX_RATE=1e4` 是**绝对边界**，设计意图是拦住
"根本不像汇率"的量级。但绝对边界与具体币种对无关：`USD/CNY=1` 和 `=100`
都稳稳落在区间里，却离真实值差 7 倍和 14 倍。

后果比没有汇率更糟——没有汇率只会暂缓，错汇率会给出**错的结论**：
`=1` 把 100 美元变成 100 元（判成买得起），`=100` 变成 10000 元（把买得起的判成买不起）。

修法是加一层**与币种对相关**的合理性检查（锚点 ± 5 倍），并把它排在来源关卡**前面**——
一个量级不对的数字，不该靠"来源写着 official"蒙混过关。

> **教训**：一组边界值能拦住的，只有"离这组边界很远的输入"。
> 边界越宽，能拦的越少，而"看起来合法"的输入反而更多。
> 检查的粒度要贴近被检查对象的**语义**（这个币种对该是多少），
> 不能只贴近它的**类型**（一个数）。

同时把"汇率可信"拆成四层：合法性 / 合理性 / 来源可信度 / 页面内容核验。
最后一层恒为 False。这样即使前三关全过，系统也只会说"没有理由拒绝它"，
不会说"汇率已核实"——差 3%~30% 的汇率照样能过前三关，本仓库没有独立汇率源。

### 15.2 `page_price` 字段的语义是错的

上一轮把"填了 page_price 且与引用价一致"标成 `page`，名字听起来像
"引擎核对过页面"。实际上引擎手里只有三个字段：`page_price`、`matched`、`url`，
**没有任何页面内容**，它做的只是自洽性检查（两个数是否相等）。

诚实链路 vs 宣称链路：

| 手里有的东西 | 引擎能验证什么 | 该叫什么 |
|---|---|---|
| `url` | 链接格式合法 | `source` |
| `+ page_price` | 两个数自洽 | `reported`（自述） |
| `+ page_text` / `page_price_set` | 哈希自洽 **且** 正文里确有这个价 | `content` |

三种加固方案都做了评估：

1. **页面文本片段**——已实现。取证方带回 `page_text`。
2. **内容哈希重算**——已实现，但**只能证明"这段正文没被改过"**，
   证明不了正文来自那个 URL。它的价值有限，不能拿来宣称"内容已核实"。
3. **报价上下文验证**——已实现，**这是三者里唯一能真正证伪的**：
   在正文里找不到这个价，就说明这条证据是错的。

堵不住的是"取证方贴一段自己写的、哈希自洽的正文"。Q7 把它固化成断言：
**这是已知限制，不是已修好的功能。** 要治本只能靠取证方把页面片段（而非一个数字）
作为强制字段带回来，引擎无法验证取证过程本身。

### 15.3 冲突判定必须先分组，再比大小

把"官方 1099"与"官方 899"塞进同一个列表、算出 22% 差异、判"至少有一个是错的"——
这个推理缺了前提：**它们是不是同一把尺上的数**。

官网建议零售价、授权商城促销价、128GB 与 256GB、国行与美版、含税与不含税，
两两都可以同时为真。把它们当冲突，规则就退化成"有两个报价就别买"。

修法是先按（口径 / 规格 / 地区）分组：

- 同组（三者都对得上）内同等级差 5% 以上 → 真冲突，暂缓；
- 不同组 → `EV_PRICE_BASIS_DIFF`（警告），**不是错误**；
- 到手价按优先级取一组（含税 > 成交 > 促销 > 标价 > 不含税），
  输入价只与这一组比——含税 1099 与不含税 899 并存时，用户说 899 仍然是暂缓，
  因为到手价是 1099。这正是"判冲突"会掩盖掉的真问题；
- 规格或地区并列、又没标要买哪个 → **缺信息暂缓**，
  但 `from` 是 `PRICE_BASIS_AMBIGUOUS`（"分不出该拿哪个价比"），不是"数据打架"。

> **教训**：差异有两种来源——**数据错了**和**口径不同**。
> 前者应该阻断，后者应该说明。把两者都当成前者，会让规则越来越不敢下结论；
> 都当成后者，会让真错误溜过去。区分它们的唯一办法是问"这两个数可不可以同时为真"。

分组时还有一个坑：只取最高等级那一档会把"官网标价（official）+ 授权商城促销
（authorized_retail）"里的促销价排除掉，反而把合法的促销误判成"输入价与官方价不符"。
所以分组范围是**所有可信来源（≤3 级）**，组内再取最高等级。

### 15.4 还没解决的

- 锚点表是**静态**的（2026-10 前后）。它拦得住量级错误，拦不住差 3%~30% 的汇率；
  距基准日超过 365 天会自动放宽到 50 倍，等于放弃这一关。真正的解法是接独立汇率源。
- 5 倍这个倍数照着**当前 9 个币种近三十年的波动区间**定的（最极端的 JPY/CNY
  漂移也只有 1.8 倍）。新增 VND / IDR 这类小面额币种必须重新校准，否则误杀真实汇率。
- `content` 级仍无法自证正文来自页面（15.2）。
- 同级冲突 5% 与输入价口径 5% 仍共用一个阈值，未按品类分化。
- 采用证据价后重算整条链路仍未实现。
- 真实网页探测仍是一次性抓取 + 离线回放（本次重抓 body sha256 与上一版一致，
  说明页面在此期间没变，但这只是一次观测，不是长期保证）。
- 自然语言链路（真实会话调用）仍未重跑。

> v0.9 对上面一部分做了收口，见 16.9「v0.8 遗留问题的处置」。

## 十六、v0.9：证据要「同一件东西」，汇率要「同一把尺」

v0.8 把七个"过了闸门"的洞堵住了，但堵的方式是**在闸门上加条件**。
这一轮回头看，七个缺陷里有五个是同一个根因的不同表现：

> **引擎一直在比数字，却从没确认这些数字说的是同一件东西、同一把尺。**

- P1/P2：比的是"页面上有没有这个数"，不是"这个数在页面里是不是价格"；
- P3：比的是价格，却没确认是同一个规格、同一个地区、同一个口径；
- P4：替代品比的是"用户价 ±5% 以内的报价"，先把不听话的证据删了再比；
- P5/P6：汇率有锚点表，却没检查锚点表**有没有覆盖这个币种**，
  `base` 参数是个摆设，同币种对有两个汇率时静默取最后一个；
- P7：低等级证据能否决高等级证据，一条 `ugc` 的脏数据就能让整单暂缓。

于是这一轮没有继续加条件，而是把"怎么审一批报价"抽成**一个函数**，
标的和替代品都走它：

```
证据池 → 可信（≤3 级）→ 新鲜 → 有链接 → 按身份分组
      → 同身份同口径冲突 → 到手价 → 页面校验 → 与输入价比
```

`evidence.assess_quotations()` 就是这行流程。标的走 `_target_price_defect()`，
替代品走 `_alt_price_check()`，两者只是参数不同（`subject` / `stated_price`），
核心逻辑同一份代码——**这是 P4 的真正修法**：不是给替代品补一段校验，
而是让它没有"另一段校验"可用。

### 16.1 「页面上有这个数」不等于「这个是价」（P1 / P2）

v0.8 的 `page_price_set` 被当成"取证方在页面上看到了这些数"，
于是给它发了 `content` 级。**这是把"声称"当成了"核实"。**

`content` 的定义收紧为：引擎能自己重算。三件事缺一不可：

1. 有 `page_text`（可检查的正文）——没有正文就无从查证；
2. 声明了哈希就由引擎重算（没声明 → `PAGE_TEXT_HASH_REQUIRED`）；
3. **这个数在正文里是以"价格"的身份出现的**。

只给 `page_price_set` → 最高 `reported`（自述），并且 `price_set_only=True`
明确标注"这是取证方报的数，引擎没见过页面"。

第 3 条是 P2。旧实现在正文里搜 `699`，于是：

| 正文 | 待查价格 | 旧结论 | 新结论 |
|---|---|---|---|
| 型号 X699，售价 899 | 699 | content ✅ | `PAGE_TEXT_NOT_A_PRICE` ❌ |
| 256GB 版，售价 899 | 256 | content ✅ | `PAGE_TEXT_NOT_A_PRICE` ❌ |
| 已售 699 件，售价 899 | 699 | content ✅ | `PAGE_TEXT_NOT_A_PRICE` ❌ |
| 售价 699 | 699 | content ✅ | content ✅ |
| 优惠后 699 | 699 | content ✅ | content ✅ |

判据不是更大的正则，而是 `classify_number(text, n)` 的四值分类：
`price`（有价格语义）/ `non_price`（型号、容量、销量、评价数、页码……）/
`unknown`（孤立的数）/ `ambiguous`（既有价格线索又有非价格线索）。
只有 `price` 通过，`ambiguous` 走 `PAGE_TEXT_PRICE_AMBIGUOUS` 让人来看，
其余一律不通过。

> **为什么不做成"更聪明的正则"**：型号、容量、销量这三类会无限增长，
> 穷举永远追不上；而"什么算价格"是封闭的（货币单位 + 价格关键词 + 非价格上下文）。
> 把开放集留给 `non_price` 兜底，把封闭集写成规则，这是能测的边界。

顺带把两个被混为一谈的概念拆开：

- `text_integrity`：**正文与声明的哈希一致**（SHA256 重算，能证）；
- `source_authenticity`：**这段正文确实来自那个 URL**（**永远 `unverified`，引擎证不了**）。

文档里不许再出现"内容已核实 = 页面确实如此"。

### 16.2 先认东西，再比价格（P3）

旧代码的比较键是 `(口径, 规格)`，缺了型号和地区，而且：

- 用户没指定规格时，128GB 促销价和 256GB 官方价混在一组，
  到手价**挑了最便宜的那个**（默认推荐便宜规格，这是导购行为）；
- 国行和美版的价格可以互相"印证"；
- 含税 1099 与不含税 899 并存时，谁是真价靠口径优先级拍板。

新的比较键是 `(model, variant, region, price_basis)`，流程固定七步：

```
1 品牌与型号 → 2 规格/SKU → 3 地区与版本 → 4 税费与交易条件
→ 5 价格口径 → 6 来源可信等级 → 7 可比较的价格
```

关键点：**口径优先级只在身份匹配之后才生效**。
同一身份（同型号同规格同地区）下，官方价 1099 与官方促销 899 可以同时为真 → 不冲突，
到手价取优先级最高的一组；不同身份（128GB vs 256GB）→ **不是价格问题**，
是 `IDENTITY_AMBIGUOUS` → 暂缓并问用户，且**绝不默认选便宜的那个**。

用户指定了规格就按指定的来（`requested_identity()`），指定了就不用猜。

**跑自然语言链路时暴露的一处自相矛盾**：128GB 899 / 256GB 1099 那个场景，
回答里同时出现两条提示——

```
[EV_IDENTITY_AMBIGUOUS] 规格并列，不同规格不能放在一起比价……
[EV_CONFLICT]           同一商品在多个来源价差 22%……
```

前一句说"这不是同一件商品"，后一句默认它们是。这正是 v0.4 那节要防的 F5
（理由与结论打架），只不过这次打架的是两条提示之间。修法是身份并列时
**不发粗价差警告**，把价差并进身份提示（`价格从 899 到 1099`），
`EV_PRICE_BASIS_DIFF` 的措辞也改成"这批报价不是同一件商品"。

> **教训**：光靠夹具测不出这类问题——E30/E31 当时是**期待**两条同时出现的。
> 只有把整条链路跑一遍、把输出当给人看的东西读一遍才发现。
> 现在 E30/E31 用精确匹配**反向断言**了：粗价差警告再出现就算失败。

### 16.3 替代品必须走同一套审计（P4）

旧实现在验证**之前**先按用户价 ±5% 过滤替代品证据：

```
官方 899（用户说的价）+ 官方 1299  →  1299 被过滤  →  "只有一个报价，没冲突"  →  SWITCH
```

这是**先删证据再下结论**，删掉的恰恰是最该看的那条。

新实现把替代品交给 `assess_quotations(subject="alternative", stated_price=用户价)`，
与标的共享：身份识别 → 全量收集同身份可信报价 → 同等级同口径冲突检查 →
到手价 → 与预算比 → 才谈 SWITCH。

效果：899/1299 两个官方价同时存在 → `ALT_PRICE_CONFLICT` → DEFER。
**代价**：SWITCH 变少了。这是对的——替代品本来就该和标的同样难通过，
否则"换个更便宜的"就成了绕过审计的后门。

### 16.4 汇率：锚点缺失不再是"通过"（P5 / P6）

P5 的根因很朴素：`FX_ANCHORS` 有 9 个币种，`SUPPORTED_CURRENCIES` 有 12 个，
多出来的 3 个（如 VND）**没有锚点**。旧代码 `expected is None` 时直接 `ok=True`——
"没有参照就等于没问题"。

现在：

- `fx_anchor_gaps()` 列出所有缺锚点的币种；
- `fx_anchor_coverage_ok()` 是**断言**，被 `tests/check_repo.py` 调用：
  以后新增币种不配锚点，`check_repo` 直接 FAIL；
- `fx_plausibility()` 遇 `expected is None` 返回 `FX_NO_ANCHOR`（拒绝），
  不再静默放行。

P6 是 `base` 参数：它以前是装饰品——`fx_rates()` 把所有币种对塞进表里，
谁通得到基准币根本没检查。现在明确定义：

- `base`/`quote`：`1 quote = rate base`，换算一律**乘** `rate`；
- 只有**能通到基准币**的币种对才进表（默认 `FX_CROSS_DEPTH=1`，
  即允许一次交叉：EUR→USD→CNY）；
- 同一币种对出现两个汇率且差异 >1% → **整对丢弃**（含反向），冲突单独报出；
- 反向汇率不一致（>5%）→ 两条都丢；
- 与本次换算无关的币种对（走不到 base）→ `FX_UNRELATED_PAIR` 排除。

`conversion_rate()` 返回 `(rate, chain)`，`chain` 记录换算路径；
交叉换算会在 findings 里留一条 `EV_FX_CROSS_USED`（INFO），**不静默**。

> **明确不做的**：静态锚点只拦量级错误（差几倍、几十倍），
> 拦不住差 3%~30% 的汇率。不为了"有汇率"去接一个不可靠的免费源——
> 一条错的汇率比没有汇率更危险，因为它会看起来正常。

### 16.5 低等级证据只能当提示（P7）

旧代码里，一条 `ugc`（5 级）证据带着 `page_price=0`，
经过页面校验 → `PAGE_PRICE_NOT_FOUND` → **BLOCK**，把整单打成 DEFER。
一条劣质证据否决了一堆有效证据。

新规则按来源等级分两类处理：

| 证据等级 | 能否参与成立报价 | 发现的问题 |
|---|---|---|
| ≤3（官方/授权/第三方） | 能 | 按原规则阻断 |
| 4~5（用户自述/UGC） | **不能** | 降级为 `ADVISORY`（提示），记在 findings 里，不进决策 |

同时三条不能破的底线：

- 同等级、同身份、同口径的真冲突 → 仍然暂缓（不因为"要给出结论"就放行）；
- 高等级证据自身有问题 → 仍然正常阻断（等级不是免死金牌）；
- 一条可信报价都没有 → 仍然不给 BUY / SWITCH。

> **反面也要防住**：这轮没有"把低等级证据全删了"。
> 它们仍然进 findings，仍然能在"为什么暂缓"里被提到——
> 只是不能**否决**一条独立成立的高等级证据。

### 16.6 这一轮的测试纪律

- **先复现旧行为**：七个缺陷逐条用修复前的代码跑出错误输出，
  存 `tests/repro/round9-old-behaviour.txt`，改完之后回来对照。
- **每个缺陷一个反例夹具 + 一个反向对照**：
  - 反例：型号 699 不能通过 → 正向对照：「售价 699」必须通过；
  - 反例：只有 `page_price_set` 不给 content → 正向对照：带 `page_text` 且哈希一致给 content；
  - 反例：低等级不能否决高等级（应 BUY）→ 反向对照：**只有**低等级证据时必须 DEFER。
- **变异测试 75 条，全部被捕获，0 条"只崩溃"**：
  崩溃不算捕获（`SURVIVED·崩溃`），因为崩溃只是说明有人动过那行代码，
  说明不了断言真的看着了这个语义。
- 本轮新增的 13 条变异（m63–m75）**每一个都对应本轮的一个具体修法**：
  `page_price_set` 冒充 content、数字一律当价格、身份歧义被忽略、
  替代品恢复 ±5% 预过滤、缺锚点放行、同币种对取最后一个、
  交叉深度无限制、低等级重新获得否决权、替代品改用简化标准……

### 16.7 阈值与参数（本轮新增）

| 参数 | 值 | 依据 / 说明 |
|---|---|---|
| 同币种对冲突阈值 | 1% | 汇率源之间的一致性应远高于此；差异超此值视为"至少一条是错的" |
| 反向汇率一致阈值 | 5% | 反向汇率常来自不同时点，放宽一档 |
| `FX_CROSS_DEPTH` | 1 | 允许一次交叉；更深链路不确定度累积，宁可拒绝 |
| `FX_MIN_RATE` / `FX_MAX_RATE` | 1e-4 / 1e4 | 量级闸门（v0.8 沿用） |
| `FX_PLAUSIBLE_FACTOR` | 5 | 与静态锚点的偏离倍数（v0.8 沿用） |
| 可信来源等级上限 | 3 | `credible_max_tier`（v0.6 沿用） |
| 同级冲突 / 输入价偏差 | 5% / 2% | 经验值，仍未按品类分化（**已知限制**） |

### 16.8 还没解决的
