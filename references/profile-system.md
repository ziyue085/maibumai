# 个人画像系统

## 一、为什么不是"一个用户档案"

大多数助手会存一句"用户是学生，预算有限"。这句话三个月后就错了，而且会污染所有判断。

这里**按事实存**：每条可独立确认、可独立过期，带日期与来源。

```json
"finance.liquid_cash": {
  "value": 32000,
  "updated_at": "2026-08-31",
  "source": "用户资产快照 2026-08-31",
  "confirmed": false
}
```

`confirmed: false` 表示"这是历史记录，用户还没确认现在还是这样"——**不参与任何计算**。

**这条对"会改变算式结果"的字段一律生效**，不只是收入支出：

| 字段 | 为什么必须确认才算数 |
|---|---|
| `finance.discretionary_override` | 一个没确认的覆盖值能让 4000 元瞬间变成"在预算内" |
| `finance.spendable_override` | 同上，等于"存款都能花" |
| `finance.single_purchase_threshold` | 抬高门槛就能把重决策降成常规决策，审核强度直接掉一档 |
| `invest.expected_annual_return` | 没确认的收益率会变成"十年后是多少"的复利结论 |

另外两条同源规则：

- **没有日期 = 不可信**。手写一份不带 `updated_at` 的画像不能绕过时效检查。
- **类型不对 = 不可信**。声明为 `number` 的字段填了"两千六"，按未知处理，不猜也不崩。

## 二、六层财务：存量与现金流必须分开

这是整套判断的地基。把两者混在一起，就会得出"月入 800 不能买 4000 的东西"这种荒谬结论。

| 层 | 字段 | 作用 |
|---|---|---|
| ① 净资产及构成 | `net_worth`、`liquid_cash`、`invest.capital`、`receivable`、`liabilities` | 看清全局，**不等于可消费金额** |
| ② 可动用现金 | `liquid_cash` | 能立刻拿出来的部分 |
| ③ 应急与必要储备 | `emergency_fund`、`near_term_obligations` | 已经名花有主，不能算可花 |
| ④ 已安排用途 | 即 ③ 两笔 | 学费、房租、还款、押金 |
| ⑤ 可自由消费资金 | 计算值 = ② − ③ | 一次性大额的真实来源 |
| ⑥ 每月现金流 | `monthly_income`、`monthly_fixed_expense`、`savings_target_monthly`、`monthly_contribution` | 决定这笔钱会不会挤掉日常 |

```
月结余 = 收入 − 固定支出 − 储蓄目标 − 月投资
可自由消费资金 = 现金 − 应急金 − 近期必要支出
```

**三条硬规则**：

1. 投资资产**默认不动用**。要动，显式设 `finance.spendable_override`。
2. 应收款**不算现金**——钱还没到手。
3. 现金填了、应急金没填 → **可自由消费资金是"未知"**，不是"等于现金"。
   引擎会拦住大额判断，让你先问，而不是替他把存款都算成能花。

## 三、可承受性怎么算（不再用"6 倍月收入"一刀切）

判定顺序：

```
1. 超过用户自设的单笔硬上限        → 不建议购买（一票否决）
2. 月结余覆盖得了                 → 可以买（现金流内）
3. 可自由消费资金覆盖得了         → 可以买（动存量），超过一半则提示
4. 覆盖不了，但存量 + 一年结余够    → 建议暂缓（要攒、要跨月）
5. 连"存量 + 一年结余"都不够       → 不建议购买（安全底线）
6. 关键数据缺失                   → 先问，结论降为暂缓
```

第 2 步要小心一件事：**储蓄目标或每月投资没填时，月结余只是上界。**
引擎会算出这个数，但会标记 `surplus_basis = estimated`；
如果这笔消费吃掉上界的一半以上，就不会拿它去支撑"买得起"——结论降为暂缓，并说明缺什么。
吃掉不到一半时照常判，因为缺的两项要吃掉六成才翻转结论。

**为什么不是 6 倍**：6 倍是"几个月工资"的直觉，适合工资稳定、没有存量的人。
对**有储蓄但收入不稳定**的人（学生、自由职业、间歇接活），问题从来不是"月收入撑不住"，
而是"这笔钱该不该从存量里出"。用 6 倍当红线，等于把他们的储蓄当不存在。

一年结余 + 存量仍覆盖不了，才算真正的安全风险——那是"砸锅卖铁也买不起"的量级。

## 四、已有资源：先问"现有的够不够"

买设备、服务器、会员、软件之前，必须先看清单。

登记的物品除了名字和状态，还能带**每月成本**与**在用状态**：

```json
{"name": "腾讯云服务器", "category": "云服务/服务器",
 "condition": "good", "status": "active", "monthly_cost": 60}
```

引擎会算出：

- `similar`：与本商品**子品类相同**或名称有词元重合的在用资源
- `monthly_subscription_total`：当前在用服务每月合计

**匹配只看子品类**（`数码/耳机` 对 `数码/耳机`），不看顶层品类。
否则买平板时会把手机、笔记本全算成"已有同类"，提示变成噪声，最后没人看。

判定时优先回答四个问题：

1. 现有的能不能满足？不能的话，差在哪一项？
2. 新的会不会和现有的重复？（尤其是**功能重叠的订阅**）
3. 是否真的减少时间成本与维护负担？还是多一个要照看的东西？
4. 免费额度结束后要花多少钱？续费价是多少？

如果模型给出了"建议购买"，却完全没提已有同类资源，审计会给一条警告——
**不否决，但不能装作没看见**。

## 五、初始化：候选稿 + 逐个确认

历史快照（比如"某年某月某日的资产盘点"）不能直接用，要走 `seed`：

```bash
python scripts/mbm.py seed --input candidate.json
```

候选稿格式：

```json
{"facts": {
  "finance.liquid_cash": {
    "value": 32000, "observed_at": "2026-08-31",
    "source": "用户资产快照", "confirmed": false
  }
}}
```

写入后：`confirmed: false`，日期保持原样，`brief` 里显示"（2026-08-31 记录，待确认）"。
用户说"还是这个数"，跑 `profile confirm --key finance.liquid_cash` 才算数。

**默认不覆盖已确认的值**，除非 `--force`。

首次使用只问最影响结论的三项：

1. 每月固定进账多少？
2. 每月固定支出多少？
3. 每月投到投资 / 存起来的钱多少？（没有就答 0）

有这三项就能算月结余。存量三项（现金、应急金、近期必要支出）**等遇到大额消费再问**，
不要一上来填十个空。

## 六、维护：三种状态，三种处理

| 状态 | 含义 | 处理 |
|---|---|---|
| 缺失 | 从没填过 | 遇到相关判断再问 |
| 待确认 | 有历史值，但没确认 | 问一句"还是这样吗"，确认或更新 |
| 过期 | 填过、超过保鲜期 | 同上；**不假设仍然有效** |
| 无日期 | 有值但没有 `updated_at` | 按未知处理，问清什么时候的数 |
| 类型不对 | 数字字段填了文字 | 按未知处理，让用户改成数字 |

保鲜期：收入 90 天（收入可能不稳定）、现金 90 天、负债 90 天、支出/储蓄/投资 180 天、偏好与身份 365 天。

用户拒答时，明确说"这条我按上次的数字算，可能不准"，并在结论里标注——不要沉默地用过时数据。

## 七、判断只看数字与约束，不看身份标签

两条对称禁令：

- **不因为"有储蓄"就默认消费没压力。** 存款有它的用途（应急、投资、目标），不是可以随便消耗的余额。
- **不因为"是学生"就一律劝省。** 身份不进入任何计算。

进入计算的只有：可自由消费资金、月结余、硬上限、硬约束、以及这笔消费本身的价值。

同一个人买 300 元的演出票和 3000 元的设备，标准一样：需求真假、买法优劣、承受能力。
**唯一不同的是数字，不是标签。**

## 八、投资收益率：假设，不是承诺

`invest.expected_annual_return` 是用户自己设的**假设**，用于把消费折算成"这些钱如果拿去投资会怎样"。

规则：

- 没设 → **完全不出现**复利数字。
- 设了 → 必须同时说明"这是假设，实际可能亏损"，且不能反复强调。
- **不做复利恐吓**。把"十年后是多少"当成反对购买的理由，是最容易也最下作的劝退手法。

消费的收益是真实的：情绪价值、便利、效率、少受的罪。它们要进决策，不能被折现成一个吓人的数字抹掉。

## 九、隐私边界

| 位置 | 内容 | 入库 |
|---|---|---|
| `~/.maibumai/profile.json` | 真实财务、偏好 | ❌ |
| `~/.maibumai/owned.json` | 真实设备与服务清单 | ❌ |
| `~/.maibumai/decisions.jsonl` | 真实消费记录 | ❌ |
| `templates/*.json` | 结构模板（全空值） | ✅ |
| `tests/fixtures/persona.sample.json` | **虚构**测试画像 | ✅ |

三重防护：数据目录在仓库外、`.gitignore` 兜底、`doctor` 扫描仓库内是否出现个人数据文件。

## 十、为通用化留的路

规则引擎里**没有任何一处写死具体的人**：

- 单笔门槛 = `max(500, 月结余 × 25%)`
- 硬约束来自用户自己声明的开关
- 复利只在给了收益率时才算
- 结论由通用的 23 条规则码解析

换一个人，只需要换一份 `profile.json`，代码一行不改。
