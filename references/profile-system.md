# 个人画像系统

## 一、为什么不是"一个用户档案"

大多数助手会存一句"用户是学生，预算有限"。这句话三个月后就错了，而且会污染所有判断。

所以这里**按事实存**：每条是一个可独立确认、可独立过期的值。

```json
"finance.monthly_income": {
  "value": 2500,
  "updated_at": "2026-10-29",
  "note": ""
}
```

好处：

- 收入变了只改一条，不用重写整个档案。
- 半年前填的收入会自动变成"待确认"，而不是被当成事实继续用。
- 每个字段能说清"为什么要问"——问不出来的字段就不该存在。

## 二、字段清单

### 财务（决定"买不买得起"）

| 字段 | 保鲜期 | 为什么需要 |
|---|---|---|
| `finance.monthly_income` | 180 天 | 承受力的起点 |
| `finance.monthly_fixed_expense` | 180 天 | 扣掉固定开支才有可支配余额 |
| `finance.savings_target_monthly` | 180 天 | 储蓄目标优先于可选消费 |
| `invest.monthly_contribution` | 180 天 | 这笔消费最直接的替代用途 |
| `finance.emergency_fund` | 365 天 | 应急金不足时不该做大额可选消费 |
| `finance.hard_cap_single` | 365 天 | 单笔绝对上限，超过直接不建议购买 |

**可支配余额是算出来的，不是问出来的：**

```
月可支配 = 月收入 − 固定支出 − 储蓄目标 − 每月投资额
```

收入 2500、固定支出 1200、投资 300 → 可支配 1000。
所以一笔 18000 的相机等于 18 个月的全部可支配余额——这个数字比任何劝说都有力。

用户也可以直接指定（`finance.discretionary_override`），适用于收入波动大或家庭共同开支的情况。

### 投资（把消费翻译成机会成本）

| 字段 | 保鲜期 | 为什么需要 |
|---|---|---|
| `invest.capital` | 180 天 | 看这笔钱占投资本金的比例 |
| `invest.monthly_contribution` | 180 天 | 消费直接挤占这一项 |
| `invest.expected_annual_return` | 365 天 | **只用于机会成本演示，没填就不算** |
| `invest.plan` | 365 天 | 判断这笔消费是否与计划冲突 |

年化预期**绝不替你假设**。填了 8%，才会算"1000 元十年后是 2159 元"；没填，这个数字根本不出现。

这条限制很重要：编一个收益率去做复利恐吓，是最容易也最下作的劝退手法。

### 生活与偏好（决定"换成什么"）

| 字段 | 为什么需要 |
|---|---|
| `life.stage` / `life.living` | 宿舍放不下大件；有无厨房决定厨电是否有意义 |
| `pref.price_sensitivity` | 决定替代方案推荐的激进程度 |
| `pref.quality_vs_price` | 决定往"更便宜"还是"更耐用"方向换 |
| `pref.used_ok` | 二手指南是常见的高性价比路径，但不是人人都接受 |
| `pref.durability_weight` / `pref.convenience_weight` | 影响是否建议加钱买更省事的 |
| `interests.list` | 判断这笔消费是否服务于长期兴趣，而不是一次性冲动 |

### 约束（硬边界，引擎强制）

三项结构化开关，违反即**不建议购买**：

- `no_used`：不买二手
- `no_subscription`：不再增加订阅
- `must_be_portable`：必须可携带（搬家、宿舍场景）

另有 `constraints.notes` 放自由文本，由模型自行判断，不做引擎强制。

## 三、初始化：不要一次问十个

首次使用时，只问**最影响结论的三项**：

1. 每月固定进账大概多少？
2. 每月固定支出大概多少？
3. 每月投到投资里的钱大概多少？

有这三个就能算出可支配余额，能拦住"月入 2500 想买 18000 相机"这类判断。

其余的（储蓄目标、应急金、硬上限、偏好、兴趣）在后续对话里**遇到再补**：

- 讨论订阅时，问一句"你能接受订阅吗"
- 讨论二手时，问一句"二手可以吗"
- 讨论大件时，问一句"有没有一条单笔不越过的线"

这比一次性 15 个问题有效得多，也不会让人一上来就放弃。

## 四、维护：过期要确认，不要假设

`mbm.py profile gaps` 会列出缺失与过期的字段，按优先级排序。

- **缺失**：从没问过。
- **过期**：填过，但超过保鲜期（收入 180 天、偏好 365 天）。

过期的处理只有两种：

1. 问一句"收入还是 2500 左右吗"，用户说"是"，跑 `profile confirm`；
2. 用户给了新数字，跑 `profile set`。

**不允许**：拿半年前的收入继续算可支配余额，还假装它是准的。

如果用户不想回答，就明说"这条我按上次的数字算，可能不准"，并在结论里标注不确定性。不要沉默地用过时数据。

## 五、判断只看数字，不看身份标签

两条必须遵守的对称禁令：

- **不因为"有储蓄"就默认消费没压力。** 有 5 万存款，和"这笔 8000 该不该花"是两个问题——存款有它的用途（应急、投资、目标），不是可随意消耗的余额。
- **不因为"是学生"就一律劝省。** 身份不进入任何计算。进入计算的只有：可支配余额、硬上限、应急金、约束、以及这笔消费本身的价值。

同一个人买 300 元的演出票和买 3000 元的相机，判断标准一样：需求真假、买法优劣、承受能力。**唯一不同的是数字，不是标签。**

## 六、隐私边界

| 位置 | 内容 | 是否入库 |
|---|---|---|
| `~/.maibumai/profile.json` | 真实财务与偏好 | ❌ 在仓库之外 |
| `~/.maibumai/owned.json` | 真实物品清单 | ❌ |
| `~/.maibumai/decisions.jsonl` | 真实消费记录 | ❌ |
| `templates/profile.template.json` | 结构模板（全部为虚构示例） | ✅ |
| `tests/fixtures/persona.sample.json` | 虚构测试画像 | ✅ |

三重防护：

1. 数据目录默认在仓库外，`git clone` 拿不到任何个人数据。
2. `.gitignore` 屏蔽 `profile.json` / `decisions.jsonl` / `*.local.json`。
3. `mbm.py doctor` 会扫描仓库内是否出现个人数据文件，并检查数据目录是否落在 Git 工作树内。

## 七、为将来通用化留的路

规则引擎里**没有任何一处写死"学生"或某个具体金额**。

- 阈值从画像推导：单笔门槛 = `max(500, 月可支配 × 25%)`
- 硬约束来自用户自己声明的开关
- 机会成本只在你给了收益率时才算
- 结论由通用的 22 条规则码解析

换一个用户，只需要换一份 `profile.json`，代码一行不改。这也是为什么画像必须独立于规则存在。
