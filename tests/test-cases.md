# 测试用例说明

## 一、设计原则

**每条用例都对应一个会真实发生的场景，不是为凑覆盖率编的。**

判断一条用例好不好，问三个问题：

1. 这个场景真实存在吗？
2. 如果系统在这里出错，用户会受损吗？
3. 出错的表现是什么？能不能写成断言？

第 3 条最关键。写不成断言的用例，只能进人工回归清单（见 `regression-checklist.md`）。

## 二、四层分工

| 层 | 文件 | 测什么 | 数量 |
|---|---|---|---|
| verdict | `cases/verdict_cases.json` | 规则码 → 结论是否正确 | 20 |
| audit | `cases/audit_cases.json` | 输出是否自洽、具体、可核验 | 13 |
| evidence | `cases/evidence_cases.json` | 来源、时效、冲突、日期越界 | 13 |
| calc | `cases/calc_cases.json` | 算术与分级 | 15 |

## 三、重点用例

用户点名要关注的五类场景，对应关系：

| 场景 | 用例 | 断言 |
|---|---|---|
| **合理享受型消费** | V01、V02 | 必须给出"建议购买"，判成暂缓即失败 |
| **冲动消费** | V03、V11、V15 | 必须拦下或暂缓 |
| **信息不足** | V11、V16、A01、A08 | 暂缓 + 必须有复查条件；缺理由不得给结论 |
| **价格过期** | V09、E02、E10、A11、A12 | 过期价格不得支撑购买结论 |
| **错误推荐** | V05、V14、A02、A06、A07 | 不得推荐错误型号；不得凭口述价断言价格合理；不得无理由否决 |

## 四、反向对照（防"一律拦截"）

只有"该拦的拦住了"是不够的——一个永远输出"不建议购买"的系统也能通过所有拦截测试。

所以每个检查器都有反向对照：

- **V01/V02**：合格的享受型消费必须放行。
- **V10（audit）**：完全合格的决策必须零阻断**零警告**。
- **E09**：干净的官方报价必须零发现。
- **E06**：价格冲突是警告不是阻断（冲突可解释，不该一棍子打死）。

`run_regression.py` 在 `expect_ok: true` 的用例上额外断言 `warnings == 0`——出现警告也算失败。

## 五、变异测试

`mutation_check.py` 故意改坏 10 处关键规则，每次都必须至少挂一条用例：

| 变异 | 捕获于 |
|---|---|
| 把「已有同类」从硬拦截降级 | V03 V04 V17 V18 |
| 把「价格过期」当作正向理由 | V09 |
| 取消「为什么需要」锚点要求 | V01 V02 A10 |
| 放宽电子品价格保鲜期到 999 天 | E02 A11 |
| 放宽价格冲突阈值到 50% | E06 |
| 删掉废话检测词表 | A04 |
| 删掉最高级表述检测 | A05 |
| 允许一条理由就下结论 | A13 |
| 把用户口述价格当官方报价 | A02 |
| 让空替代品也算有效替代方案 | A09 V06 |

**如果某个变异没被捕获，说明对应用例是空转的**——它没有真正约束任何东西。

## 六、端到端

`run_cli_smoke.py` 用临时数据目录跑完整生命周期，验证：

- 数据目录能创建，且不在 Git 仓库内
- 画像能写能读
- 已有物品能登记能检索
- 草稿能校验、结论能解析
- 账本能写、能标记已购、能记录复盘
- 统计能算出闲置率、后悔支出、高估倍数
- 已复盘的不再出现在待办
- 能导出 Markdown
- **审计不通过时拒绝落账**

最后一条尤其重要：如果 `log` 无条件接受任何输入，前面所有校验都可以被绕过。
